## 3. GitHub Actions 首次部署

推荐流程为：配置 GitHub Secrets → Actions 自动检查服务器环境、创建独立目录、启动容器、发布官网。无需从开发者本机登录服务器，也无需先执行本地部署脚本。

### 3.1 前置条件

服务器需已有 Docker Compose、Python 3.9+ 与 Linux `flock`；脚本不自动安装这些组件。`alvis` 需有 `/srv/daywish` 写入权限，并有 Docker 使用权限或免密 `sudo docker` 权限；首次没有该目录时，Actions 通过免密 sudo 创建由当前登录用户持有的独立目录，已有目录不更改归属。

这些检查由工作流执行。8085 被其他服务占用时停止，不修改宿主机已有的域名转发。全程初始化使用服务器文件锁，避免同时发布两个平台时互相干扰。

### 3.2 推送源码

本轮已经提交并核对源码出现在远端。后续修改可在具有 Git 写入权限的终端执行：

```powershell
git add .
git diff --cached --check
git commit -m "feat: 好日将至双端客户端与官方网站"
git push -u origin main
```

推送前检查暂存区；`.gitignore` 已排除安装包、构建结果、缓存、个人 AI 配置、环境文件及密钥文件。安装包不放进 Git 历史，作为 GitHub Release 附件和服务器下载文件发布。不使用 force push。

### 3.3 本地备用部署入口

以下仅为备用方式，使用 GitHub Actions 时不需要运行：

```powershell
.\scripts\部署官网.ps1 -SshTarget alvis@152.136.107.93 -IdentityFile C:\Users\admin\.ssh\nest_home_deploy
```

脚本仅构建官网，不重新打包客户端；校验本地 v0.2.2 安装包，再使用指定密钥上传。服务器建立独立的 `daywish-website` 容器：

```text
daywish.alvis.org.cn
        ↓ 宿主机现有 Nginx
127.0.0.1:8085
        ↓
daywish-website 容器 :8080
```

服务器目录：

| 路径 | 内容 |
|:--|:--|
| `/srv/daywish/service/` | 官网容器与站点配置 |
| `/srv/daywish/sites/` | 每次官网静态构建的独立目录 |
| `/srv/daywish/current` | 指向当前官网目录的符号链接 |
| `/srv/daywish/downloads/` | 按版本保存的不可变安装包 |
| `/srv/daywish/state/releases.json` | 两个平台的发布记录 |
| `/srv/daywish/incoming/` | 上传与排障暂存目录 |

归档只允许普通目录和文件，拒绝路径穿越及符号链接。每次发布把目录权限设为 755、文件设为 644；官网切换使用符号链接原子替换，保留上一版。容器绑定整个项目目录，避免绑定 `current` 时固定在旧符号链接目标。

## 4. GitHub Actions 配置

在 GitHub 仓库配置以下 Actions Variables 和 Secrets，可放在 `production` Environment 下：

| 类型 | 名称 | 内容 |
|:--|:--|:--|
| Variable | `DEPLOY_USER` | 服务器部署账号，当前默认 `alvis`，可通过变量覆盖 |
| Variable | `DEPLOY_PORT` | SSH 端口，默认 22；与官网的 8085 无关 |
| Secret | `DEPLOY_SSH_KEY` | 专用 CI 部署私钥，对应公钥已加入服务器部署账号 |
| Secret | `DEPLOY_KNOWN_HOSTS` | 已核对的目标服务器 SSH 主机公钥记录 |

主机地址已写为 `152.136.107.93`。不将私钥、密码或令牌写入仓库。首次配置 Secrets 和实际连通验证仍待有权限的环境完成；仅提交工作流文件不会使自动部署自动具备服务器登录能力。

### 4.1 一次性配置并启动 Actions

用户本人终端已有 PyNaCl 和 GitHub 登录凭据时，可在项目根目录执行：

```powershell
python .\scripts\配置GitHub部署.py --key C:\Users\admin\.ssh\nest_home_deploy
```

工具读取本机已有的受信任服务器 `known_hosts` 记录，使用 GitHub 提供的公钥及 PyNaCl SealedBox 在内存中加密密钥。写入 `production` Environment 的 `DEPLOY_SSH_KEY`、`DEPLOY_KNOWN_HOSTS`，设置 `DEPLOY_USER=alvis` 和 SSH 端口，然后触发官网工作流。不会输出私钥、令牌或明文 Secrets，不从本机执行服务器 SSH。

工具不自动安装依赖。本轮执行已确认当前环境有 PyNaCl，但读取私钥和 GitHub 登录凭据均被拒绝，因此尚未写入 Secrets。也可通过仓库 Settings → Secrets and variables → Actions 手动设置这两个 Secret：`DEPLOY_SSH_KEY` 的值为私钥文件内容，不能填文件路径；`DEPLOY_KNOWN_HOSTS` 为已经核对的服务器主机公钥记录，不能填客户端部署公钥。

### 4.2 更新官网页面

`.github/workflows/website.yml` 在 `main` 的相关源码变化时运行，也可手动触发。执行测试、官网构建、打包和 SSH 上传；首次自动初始化服务，日常更新验证后原子切换，并检查实际构建标识。公网健康检查失败时尝试回滚至上一官网。

首次没有发布安装包时，服务器初始化空的版本清单，官网显示“安装包准备中”。不会把仓库里的本地下载种子当作已上传文件。发布客户端后下载入口才自动出现。

### 4.3 自动构建客户端并更新官网

在 Actions 运行“发布客户端并更新官网下载”，选择 `windows` 或 `macos`，填写更新说明。发布前增加根 `package.json.version`；同一平台同一版本不覆盖已有安装包。

流程为：

```text
测试与平台构建、官网构建
  → 安装包 SHA-256、大小、版本记录
  → GitHub Release 草稿上传全部附件
  → 发布正式 Release
  → 初始化或更新服务器官网服务，同步实际安装包
  → 原子更新 releases.json
  → 官网下次读取显示新下载与更新记录
```

两个平台使用 `windows-vX.Y.Z`、`macos-vX.Y.Z` 独立标签；更新一端会保留另一端的已发布版本。Mac 构建脚本从根版本号写入 `.app` 元数据和 ZIP 名称，产物架构为构建 runner 架构；官网显示 Apple Silicon 或 Intel。Mac 原生编译仍需要满足现有脚本的 Xcode/macOS SDK 要求，不保证 GitHub runner 已满足，构建失败时不开启下载。

`GITHUB_TOKEN` 创建 Release 不会再触发普通 Release 事件，因此该流程直接在同一工作流的后续步骤更新官网。发布后同步失败时，可重跑失败的发布 job；已经发布且来自同一提交、同一版本记录的 Release 会复用。

### 4.4 手动上传 GitHub Release

也可手动创建草稿 Release，上传安装包并填写更新说明，全部附件就绪后点击发布。`.github/workflows/sync-release.yml` 响应正式 `published` 事件；预发布版不进入官网。

支持的文件名：

```text
Daywish-X.Y.Z-Windows-x64-Setup.exe
Daywish-X.Y.Z-macOS-arm64.zip
Daywish-X.Y.Z-macOS-x86_64.zip
```

当前每个平台接受一个安装包；Mac 应明确选择一种架构。同步时从 GitHub 下载真实文件、计算校验值，再上传服务器。若带有 `record.json`，会核对其大小、校验值和平台版本。也可手动运行该同步工作流并填写 Release 标签，处理首次同步失败的重试。

## 5. 校验与回滚

安装包先落入独立下载目录并核对 SHA-256，再更新版本清单。同一平台版本再次同步相同安装包时不重复添加；原发布时间和说明保留。同版本但内容不同会被拒绝，必须增加版本。

官网部署检查 `build.json` 是否与上传构建一致；内部检查失败会恢复旧的 `current` 指向。服务器可手动执行：

```bash
python3 /srv/daywish/incoming/某次上传目录/deploy.py rollback-site
```

回滚官网不会删除客户端安装包或改变版本清单。安装包替换、卸载服务或更改宿主机 Nginx 不在自动回滚范围内。
